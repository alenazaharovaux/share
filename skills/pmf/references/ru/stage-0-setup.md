# Stage 0 — Setup

**Цель:** собрать базовый контекст продукта и команды, чтобы Stage 1 (Hypothesis) могла начать работу с полной картой переменных. Это короткая стадия (10-20 минут), но без неё все последующие стадии теряют опору.

**Reads:** —
**Writes:** `00_setup.md`

---

## Когда запускается

Auto-start обнаруживает одно из:
- Папка проекта только что создана (пустая)
- В папке нет ни одного артефакта
- Пользователь явно сказал «новый PMF для X»

Если в папке уже есть `00_setup.md` — Stage 0 пропускается, переход сразу к Stage 1.

---

## Шаг 0.1 — Имя продукта и slug

**Спросить:**
1. **Полное имя продукта** — как ты будешь его называть в narrative
2. **Slug** — короткое имя для папки, lowercase, через дефис (например, `cloud-research-ai-pipeline`, `bogdana-easter`, `znalica-paid-tier`). Если пользователь не предлагает свой — предложить вариант на основе имени продукта и подтвердить.

**Создать папку:** `<projects_path>/<slug>/` (где `<projects_path>` берётся из `~/.claude/skills/pmf/config.md`, по умолчанию `~/pmf-projects/`)

Если папка с таким slug уже существует — спросить: «Продукт `<slug>` уже есть. Это тот же или другой? Если другой — выбери другой slug».

---

## Шаг 0.2 — Тип продукта

**Спросить, выбрав один из вариантов:**

| Тип | Примеры |
|-----|---------|
| **B2C SaaS** | приложение / сервис для частных лиц с подпиской или paid features |
| **B2B SaaS** | сервис для компаний (продаётся менеджерам, используется сотрудниками) |
| **Marketplace** | площадка соединяющая две стороны (покупатель↔продавец, заказчик↔исполнитель) |
| **DTC (Direct-to-Consumer)** | физический продукт продаваемый напрямую пользователю |
| **Services / Consulting** | услуга которую оказывает человек или команда (исследования, дизайн, разработка) |
| **Internal tool** | продукт для внутренних команд организации, не для продажи |
| **Other** | если не подходит ни одно — кратко описать что это |

**Почему важно:** тип определяет multi-role handling в Stage 1:
- **B2B SaaS** → Decision Makers (кто платит) ≠ End Users (кто пользуется). Нужны раздельные dimensions для каждой роли.
- **Marketplace** → Demand side (покупатели) ≠ Supply side (продавцы). Нужны раздельные dimensions + chicken-and-egg problem явно отметить.
- **Остальные типы** → одна аудитория, одна dimensions-таблица.

## Шаг 0.3 — Контекст организации

**Спросить, выбрав один из вариантов:**

| Контекст | Описание |
|----------|----------|
| **Zero-to-one** | новый продукт с нуля, нет существующих клиентов, нет каналов, нет бренда |
| **Established** | внутри уже работающей компании, есть бренд, есть каналы, есть клиенты которым можно показать |
| **Extension** | расширение существующего продукта (новая фича, новый сегмент, новый рынок) |

**Почему важно:** контекст влияет на акценты в Stage 1-3:
- **Zero-to-one** → больше внимания к Timing (Why Now) и Founder-Market Fit. Нет шортката через существующие каналы.
- **Established** → переиспользование существующих каналов, аудиторий, репутации. Главный риск — каннибализация существующего предложения.
- **Extension** → cross-fit с существующим продуктом важнее чем абсолютные цифры. Какие dimensions наследуются от родительского продукта, какие новые.

## Шаг 0.4 — Team Pre-Flight Check

**Перед** работой с продуктовыми dimensions нужен честный взгляд на команду. 3 коротких вопроса:

1. **Founder-Market Fit.** Почему именно эта команда работает над этой идеей? Есть ли у вас «earned secret» — то, что вы знаете про эту проблему/рынок благодаря личному опыту, что не знают другие?

2. **Skill gaps.** Каких ключевых компетенций не хватает в команде сейчас? (продукт / инжиниринг / sales / маркетинг / domain expertise)

3. **Conviction vs flexibility.** Насколько вы готовы радикально изменить hypothesis если данные покажут что она неверна? Шкала 1-10. (10 = полностью готовы развернуться, 1 = слишком вложились эмоционально/финансово чтобы менять)

**Risk flag** — записать в `00_setup.md`:

| Уровень | Условие |
|---------|---------|
| **Высокий риск** | нет founder-market fit + 2+ ключевых skill gaps + conviction-flex < 5 |
| **Средний риск** | одно из трёх условий выше |
| **Низкий риск** | ничего из вышеперечисленного |

**Это не блокер для продолжения** — это контекст для интерпретации остальных стадий. Если риск высокий, в Stage 2-4 приоритет — найти партнёров или советников, закрывающих gaps.

Pre-flight результаты будут перенесены в `narrative-v1.md` в Stage 1 (отдельной секцией), чтобы быть видимыми на всех последующих этапах.

## Quality gates

Перед переходом к Stage 1 проверить:

- [ ] Папка проекта создана по правильному пути
- [ ] Slug в нижнем регистре, через дефис, без пробелов и кириллицы
- [ ] Тип продукта выбран из списка (не «не знаю»)
- [ ] Контекст организации выбран из списка
- [ ] Team Pre-Flight Check заполнен — все 3 вопроса
- [ ] Risk flag явно поставлен (Высокий / Средний / Низкий)
- [ ] `00_setup.md` сохранён в папке проекта

Если что-то не заполнено — не двигаться к Stage 1, вернуться и заполнить. Stage 1 будет ссылаться на эти данные, пропуски сломают работу с dimensions.

## Common pitfalls

| Ошибка | Как избежать |
|--------|--------------|
| «Не уверен что это B2C или B2B» | Спросить: кто реально платит — конечный пользователь или его компания? Это и есть тип. |
| Pre-flight check проводится для галочки, без честности | Тон скилла — спокойный, не оценочный. Объяснить: pre-flight не блокирует, он только настраивает приоритеты в Stage 2-4. Чем честнее — тем полезнее. |
| Conviction-flex = 10 у всех | 10 — это «я полностью развернусь если данные покажут». Реально это редкость. Обычно 5-7. 10 — флаг что вопрос не понят. |
| Slug на русском или с пробелами | Slug — это имя папки. ASCII, lowercase, через дефис. |
| Skip Stage 0 при «я и так всё знаю про мой продукт» | Не пропускать. 5-10 минут на 00_setup.md экономят часы недопонимания на Stage 1. |
| 00_setup.md пишется как «эссе про продукт» | Это структурированный контекст, не narrative. Narrative — в Stage 1. Здесь только факты которые нужны для распаковки dimensions. |

## Что НЕ делать в Stage 0

- **Не формулировать гипотезу** — это работа Stage 1
- **Не описывать problem/value prop** — это Stage 1
- **Не делать market research** — это Stage 2
- **Не приукрашивать команду** — pre-flight требует честности, иначе теряет смысл
