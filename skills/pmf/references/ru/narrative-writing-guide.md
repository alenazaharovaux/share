# Narrative Writing Guide — как формулировать narrative для PMF

**Зачем:** narrative — главный артефакт PMF skill. Это не маркетинговый текст и не технический документ. Это **проверяемая история**, которая описывает гипотезу продукта на конкретном уровне детализации.

Narrative проходит 3 версии в течение PMF цикла:
- **V1** (Stage 1, Hypothesis) — первичная гипотеза по 7 dimensions
- **V2** (Stage 3, Synthesis) — переписана после market research, с обновлёнными рисками
- **V3** (Stage 7, Interview synthesis) — переписана после field interviews, с реальными цитатами

V1 → V2 → V3 — это **отдельные файлы**, не перезапись. Сравнение версий показывает что изменилось от validation к validation.

---

## Что такое хороший narrative

Хороший narrative отвечает на 3 вопроса в первых 200 словах:
1. **Кто** конкретно этот продукт для (не «все занятые люди»)
2. **Какую боль** он снимает (visceral, не abstract)
3. **Чем отличается** от того, как они решают это сейчас

Если первые 200 слов не отвечают на это — narrative переписать.

---

## Visceral problems vs abstract

**Visceral** = осязаемая, эмоциональная, конкретная боль с временем, местом, контекстом.

**Abstract** = категорийная формулировка, с которой нельзя поспорить.

| Abstract (плохо) | Visceral (хорошо) |
|------------------|-------------------|
| «Малому бизнесу сложно управлять заказами» | «Маленькие e-commerce продавцы 4-6 часов в неделю вручную копируют заказы из Wildberries в Excel, потом в 1С — теряют по 2-3 заказа в месяц из-за человеческих ошибок» |
| «Студенты страдают от прокрастинации» | «Студенты второго курса откладывают подготовку к экзаменам до последних 3 дней, потом не спят 2 ночи, получают 3 вместо 5, и стыдятся сказать родителям» |
| «Командам сложно координироваться удалённо» | «Удалённые команды теряют 45 минут в день на async статус-апдейты в Slack, которые никто не читает, потом всё равно делают синхронный standup» |

**Тест:** замените «продавцы», «студенты», «команды» на конкретное имя. Звучит ли это как реальный человек, которого вы знаете? Если нет — слишком abstract.

**Источник visceral формулировок:** Stage 5–7 (interviews). После interviews narrative переписывается на их языке, не на маркетинговом.

## Benefits vs features

**Feature** = что продукт умеет (sync orders, generate code, analyze data).

**Benefit** = что меняется в жизни пользователя из-за этого (вернулись 4 часа в неделю, перестали терять заказы, спокойно спят ночью).

В narrative пишем **benefits**, не features. Features — для product spec, не для narrative.

| Feature (плохо) | Benefit (хорошо) |
|-----------------|------------------|
| «Real-time sync с Wildberries API» | «Заказы появляются в 1С автоматически за 10 секунд после оформления — больше не нужно следить и копировать руками» |
| «AI-powered code review» | «Junior разработчик получает фидбек на pull request за 30 секунд вместо ожидания senior часами — разблокирован, продолжает работать» |
| «Multi-language support» | «Команда из 5 стран читает один документ на родном языке, без необходимости договариваться об «общем английском»» |

**Тест:** Прочитайте формулировку. Видно ли, как меняется день пользователя? Если только про продукт — это feature.

## Flywheels — как описать механику роста

Flywheel = самоподдерживающийся цикл, в котором каждая итерация усиливает следующую. Это сильнее, чем funnel, потому что не требует постоянного притока сверху.

В narrative описываем 1-2 потенциальных flywheels:

**Пример flywheel (Notion):**
```
Кто-то делает красивый template
  → Делится в Twitter / Reddit
    → Новые users копируют template, регистрируются
      → Ремиксят его, делают свой
        → Делятся в Twitter / Reddit
          → Loop
```

**Пример flywheel (e-commerce sync tool):**
```
Продавец экономит 4 часа в неделю
  → Может взять больше заказов
    → Зарабатывает больше
      → Готов платить за upgrade
        → Tool команда инвестирует в новые маркетплейсы
          → Продавец экономит ещё больше
            → Loop
```

**Признаки слабого flywheel:**
- Нужен paid acquisition в каждой итерации (это funnel, не flywheel)
- Каждая итерация требует нового решения от команды (нет автоматизма)
- Loop замыкается через >12 месяцев (слишком медленно)

Narrative должен показать **хотя бы одно** правдоподобное место для flywheel. Без flywheel рост = funnel = бесконечный CAC = плохая Viability.

## Persona divides — кто НЕ ваш user

Самая частая ошибка V1 narrative — говорить что продукт для «всех занятых людей» / «всех малых бизнесов» / «всех студентов».

Хороший narrative явно говорит **кого исключаем**:

**Пример (e-commerce sync tool):**
- ✓ ДА: продавцы 1-3 маркетплейсов, оборот 0.5-5 млн ₽/мес, без штатного бухгалтера
- ✗ НЕТ: enterprise (>20 млн оборот, есть IT-команда — у них своё)
- ✗ НЕТ: solo selling on one marketplace (нет проблемы синхронизации)
- ✗ НЕТ: дропшиппинг (другая модель учёта)

**Persona divide** — это явное обозначение границ. Без divide вы будете строить продукт для всех и не подойти никому.

В narrative выделить минимум **2-3 группы кого исключаем** и почему (одной фразой).

## Структура narrative по 7 dimensions

7 dimensions из `references/7-dimensions.md`:
1. Customer
2. Problem
3. Why now (timing)
4. Why us (founder-market fit / unique insight)
5. Solution shape
6. Distribution / Channel
7. Business model (Monetization)

Плюс 8-я («+1»): Defensibility / Power.

В narrative каждая dimension = свой раздел (1-2 параграфа). Не объединять.

**Анти-паттерн:** «narrative = маркетинговый текст про продукт». Маркетинг — про feature/benefit. Narrative — про hypothesis.

**Размер:** V1 narrative ~600-1000 слов. V2 ~800-1200 (больше evidence). V3 ~1000-1500 (больше реальных цитат).

---

## Evidence per dimension

Каждая dimension в V2 и V3 narrative должна иметь **evidence** или явно отмечать его отсутствие:

| Уровень | Пример |
|---------|--------|
| **Strong evidence** | «По данным interviews 2026-04-05 (15 продавцов) — 12 из 15 тратят 3-6 часов в неделю на manual sync» |
| **Indirect evidence** | «Аналог в США (Linnworks) показал ARPU $89/мес на 8K customers — для RU adjusted к $30-40» |
| **Weak / no evidence** | «Команда предполагает что эта проблема существует у RU маркетплейсов, но не валидировано» |

Цель narrative — не скрывать слабые места, а **показать где weakest evidence**, чтобы знать где валидировать дальше. Narrative со 100% strong evidence во всех dimensions = wishful thinking.

## Версионирование

| Версия | Когда | Что меняется |
|--------|-------|--------------|
| **V1** | Stage 1, после первого hypothesis brainstorm | Первичная формулировка по 7 dimensions, мало evidence, много assumptions |
| **V2** | Stage 3, после market research + risk synthesis | Скорректированы dimensions с слабым evidence, добавлены analogs/antilogs, обозначены 1-3 главных риска |
| **V3** | Stage 7, после field interviews | Переписан на языке пользователей, цитаты, скорректированы persona divides, обновлены risks |

Каждая версия = отдельный файл в папке проекта: `narrative-v1.md`, `narrative-v2.md`, `narrative-v3.md`. Не перезаписывать.

**Зачем сохранять старые версии:** показывает эволюцию понимания. Часто V3 отличается от V1 настолько, что без сравнения нельзя понять что вы научились. Это самоценный артефакт.

## Structured vs prose

PMF skill использует **2 формы narrative** для каждой версии:

1. **Structured** (`template-narrative.md`) — таблица 7 dimensions с полями, evidence, validation status. Для внутреннего трекинга команды.

2. **Prose** (`template-narrative-prose.md`) — связный рассказ для стейкхолдеров (инвесторов, partners, новых hires). Та же информация, но в форме истории.

V1 обычно создаётся только в structured форме. V2 и V3 — в обеих.

## Common mistakes

| Ошибка | Симптом | Фикс |
|--------|---------|------|
| Narrative = маркетинг | Hype, восклицательные знаки, «революционный» | Это hypothesis. Calm tone, evidence, weakness явная |
| «Для всех занятых людей» | Persona слишком широкая | Persona divide: явно кого исключаем |
| Все features, нет benefits | Описание product spec | Перевернуть: что меняется в дне пользователя |
| Abstract проблемы | «Сложно управлять временем» | Visceral: время, место, конкретные числа, реальные workarounds |
| Нет flywheel | Только funnel-based growth | Найти 1 потенциальный flywheel, явно описать |
| Один файл narrative.md, перезаписывается | Нет истории эволюции | V1, V2, V3 — отдельные файлы |
| Evidence отсутствует или фейковый | «Все хотят это» | Указать источник или явно «no evidence yet» |
| 100% Strong evidence во всех dimensions | Wishful thinking | Если всё подтверждено — validation не нужна, скилл бесполезен |
| Narrative > 2000 слов | Слишком детально для V1/V2 | Сжать до core hypothesis. Детали — в research/interview docs |

## Quality gate checklist (для всех трёх версий)

- [ ] Customer dimension: имя сегмента + persona divides
- [ ] Problem dimension: visceral формулировка с временем/числами/workarounds
- [ ] Why now: что изменилось в мире/технологии/рынке за последние 1-3 года
- [ ] Why us: какой у команды unique insight (не «нам нравится эта область»)
- [ ] Solution: benefits, не features
- [ ] Distribution: 1-2 конкретных канала с гипотезой почему сработают
- [ ] Business model: pricing model + первая гипотеза price point
- [ ] +1 (Power): какая из 7 powers применима в долгосрочной перспективе
- [ ] Flywheel: 1+ замкнутый цикл описан
- [ ] Evidence: каждая dimension имеет уровень evidence (strong/indirect/weak)
- [ ] Persona divides: 2-3 группы явно исключены
- [ ] Tone: calm, без восклицаний, без «революционно/уникально/disruptive»
